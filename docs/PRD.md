# BondBack · 押金侠 — 产品需求文档（PRD）

> 版本 v1.1（2026-07-25）· 状态：**已定稿**。v1.1 依据 07-25 的产品评审重排了差异化重心，见下方「v1.1 变更摘要」。本文档是母文档（事实源），模块级拆分与验收标准见 `docs/prd/`，执行时间轴与技术选型见 `docs/plan.md`，视觉与响应式约束见 `docs/design-tokens.md`；冲突时以本文档为准。

## v1.1 变更摘要（为什么改）

外部评审的核心意见：产品最终呈现成普通的「上传文件 → AI 生成一封信」，而 Bond 解读助手这条赛道本身并不新。差异化必须是**证据驱动的退租维权闭环**，Demo 必须清楚展示三层 AI 能力，其中**第二层最重要**：

1. AI 从扣款清单、入住报告、照片、聊天截图中**提取事实**
2. AI 把**每笔扣款与具体证据、合同义务、州法条对应起来** ← 真正的壁垒
3. AI 输出**逐项结论、可直接发送的英文申诉信、下一步行动路线**

据此的结构性改动：① `AnalysisItem` 增加三轴判定与可校验证据引用（§3.4）② 分析管线改为三段式，进度动画变真实（§3.4）③ 向导改为**上传优先**，让预填魔法必然发生（§3.2）④ 零证据时切换「举证责任翻转」模式（§3.4）⑤ 结果页首屏改为账本条 + 三行结论（§3.5）⑥ 示例案例重排为**三笔扣款、三种结论**并做成零 API 全流程重放（§4）⑦ 定位文案落点从「信」改为「逐项找出可争议扣款」（§2）⑧ 06 入住留证硬砍为愿景橱窗（§6）。

**不做的事**：不加登录、数据库、更多州、chatbot 或任何边缘功能。全部精力用于把一个示例案例打磨到极好。

- **赛事**：匠人学院 TOP Coder Challenge 04 —— 房地产 × AI，48 小时做出可运行 MVP

## 2. 产品定位

- **名称**：BondBack · 押金侠
- **标题（情绪钩子）**：**房东乱扣 Bond？先别认栽。**
- **简介（证据机制，用于首页副标题 / README / 提交表单）**：
  > 上传扣款清单和入住报告，AI 按 NSW/VIC 租赁法规逐项比对证据，告诉你哪几笔不应扣、凭哪条法规，并生成一封可直接发送的英文申诉信。
- **核心场景**：退租押金维权
- **产品形态**：「报税式」结构化向导流水线。**明确不做 chatbot 对话形态。**
- **州覆盖**：NSW + VIC；其余州在下拉框中显示但标「即将支持」
- **语言**：界面全中文；申诉信正文英文 + 中文对照解释

> 文案纪律：「让房东以为你请了律师」这类以**信**为落点的表述，从主文案全部下线（可保留在视频口播）。对外一律以「逐项找出可争议扣款」为落点。

### 纠纷类型（预设 5 类 + 兜底）

| # | 类型 | 说明 |
|---|------|------|
| 1 | 清洁费 | |
| 2 | 损坏 vs 合理磨损（fair wear and tear） | |
| 3 | 提前解约扣费 | |
| 4 | 押金逾期未退 / 未存管 | |
| 5 | 拖欠租金抵扣 | 房东通常占理，AI 必须诚实判「合法别争」——这是可信度卖点 |
| 6 | 其他 | 兜底 |

一次退租常涉及多笔扣款，胜算评估须**逐项**给结论（见 §3.5）。

## 3. 用户流程

### 3.1 首页

- **首屏必须包含一张真实对照卡**（取自示例案例的地毯那张，静态复用同一组件）。投票者不点任何东西就能看到「证据 → 合同 → 法条 → 结论」长什么样——这是对抗「看起来简单」的第一道防线。
- 入口一「😤 我的押金被扣了」→ `/wizard` 真实流程
- 入口二「👀 先看个案例」→ `/sample` 零 API 全流程重放
- 往下滚：三格能力图示（读证据 / 对法条 / 出结论与信）+ **愿景橱窗**（即将支持：QLD/WA、入住留证、中介往来助手）
- 桌面端 hero 双栏（左文案+双入口，右对照卡），详见 `docs/design-tokens.md`

### 3.2 三步向导（**上传优先**）

1. **基本情况**：选州（NSW / VIC，其余禁用标「即将支持」）+ 纠纷类型（多选）
2. **上传证据**：入住 condition report / lease PDF / 房间照片 / 与房东聊天截图 / 扣款清单
   - 入住报告**置顶单独成卡**，配文「这一份最关键：它能推翻大多数扣款」
   - 可跳过，但明确告知代价（「没有它，多数结论会停在待核实」）
   - 上传即调 `/api/extract` 预填
3. **核对与补全**：字段已经自动填好，用户只需核对与补充（押金额、被扣额、退租日期、扣款明细、押金存管核实问题）

**顺序理由**：预填规则是「只填空白且未被用户修改的字段」。若金额步骤在上传之前，用户填完后预填将无事可填，魔法时刻自我抵消。上传优先让魔法**必然发生**，且「核对」比「从白填」心理阻力小得多。

**押金存管核实**（第 3 步内，渐进展开）：押金付给谁、何时支付、是否分期、是否收到确认、是否查过官方记录。仅选「没有 / 不确定」确认邮件时，只显示黄色「先核对官方记录」提示。只有官方记录查不到、适用法定期限已过且付款信息足以计算时，才显示「可能未按期存管」的红色风险提示；若 authority 有书面确认则提高等级。任何等级都不得把最高罚则写成租客自动获赔，也不得把尚未经监管机构/Tribunal 裁定的 offence 写成确定事实。

NSW 的期限取决于钱付给房东还是中介，并有独立的分期规则；VIC s 406 只适用于 provider 收到 bond 后转交 RTBA 的情形。期限计算必须由确定性代码完成，LLM 不得仅凭「没邮件」升级结论。详细契约见 `docs/prd/02-wizard.md` 与 `03a-analysis-pipeline.md`。

### 3.3 证据识别：两级职责

| 级别 | 时机 | 模型 | 产出 |
|------|------|------|------|
| 预填 | 上传瞬间 | `EXTRACT_MODEL` | 表单字段（押金额、被扣额、退租日、扣款明细、地址）——**只求快** |
| 事实提取 | 点提交后 | `FACTS_MODEL` | `EvidenceFact[]`：带 `locator`（入住报告 P3 客厅）、`quote`（英文原文）、`kind` 的结构化事实 |

- 识别失败 → **静默回退手填**，不弹错误、不阻塞流程
- lease PDF 在客户端转前几页为图片后走同一识别管线

### 3.4 AI 分析（三段式管线）

```
上传 ──► ① EXTRACT_MODEL 预填字段（快，UI 见字段扫过金色）
提交 ──► ② FACTS_MODEL   读证据 → EvidenceFact[]   「正在阅读你的入住报告…」
     ──► ③ ANALYZE_MODEL 事实 + 州法条 → 逐项结论   「正在对照 NSW 租赁法…」
```

**进度动画是真实的两段**，不是假进度——这是白送的可信度，也是第一层能力在 UI 上的可见证明。

**三板斧写死进 prompt**，并且作为**结构化字段**输出（不是自由文本）：

| 轴 | 字段 | 取值 |
|---|---|---|
| ① 损伤是否原已存在 | `preExisting` | `yes` / `no` / `unknown` / `n-a` |
| ② 合同是否真有此义务 | `contractObligation` | `exists` / `absent` / `unknown` / `n-a` |
| ③ 是否属 fair wear and tear | `fairWearTear` | `yes` / `no` / `unknown` / `n-a` |

**否命题纪律（重要）**：`contractObligation: absent`（合同无此义务）**不得直接得出 ❌**。理由：lease PDF 只渲染前几页，用部分样本断言全量缺失在逻辑上站不住。此情形一律输出 **⚠️ 待房东举证**，措辞为「你上传的合约页中未见此义务条款」，并援引 NSW s 165（房东单方索赔须在 7 日内提供退租 condition report 与支持金额的发票/报价）把举证责任翻转给房东。

**诚实条款写死进 prompt**：房东占理时必须判「✅合法，别争」并解释原因；拖欠租金抵扣默认倾向房东占理，除非证据显示例外。

**零证据模式（举证责任翻转）**：用户未上传任何证据时，产品**不猜结论**，自动切换为逐项要求房东按 s 165 出示单据的模式——信件与路线图照常产出，用户依然拿到有法律杠杆的东西，而不是一页 ⚠️。结果页顶部显式标注当前模式。

**防幻觉硬校验（服务端，不由 LLM 自律）**：
- `evidenceRefs[].factId` 必须存在于第 ② 段产出的 `EvidenceFact[]`，否则丢弃该引用
- `statuteRefs[]` 必须存在于本次注入的 `confirmed` 法条白名单，否则丢弃并把该项降级为 ⚠️
- `bondLodgementAlert.level` 由确定性代码计算，LLM 不得自行升级

### 3.5 输出（截图/视频高光）

**结果页首屏（手机 ~560px 内必须看全四件事）**：

```
房东索扣 $1,306
█████████▓▓▓▓░░        ← 账本堆叠条，三色分段
❌$780 不合法  ⚠$340 待举证  ✅$186 合法

   可争议  $1,120
   应退回至少 $3,374

• 地毯：入住报告已记录原有污渍
• 花园：合约未见此义务，该房东举证
• 水费：合法，别争

[看逐项依据]   [生成申诉信]
```

**往下依次是**：

1. **逐项对照卡**（每笔扣款一张，固定四行结构）：
   - `证据` — 引语 + 来源定位，**可点击滚动高亮到证据原件**
   - `合同` — 三轴中的合同义务判定
   - `法条` — act + section + 原文引语 + 来源链接
   - `结论` — ❌ / ⚠️ / ✅ + 中文解释 + 该项可争议金额
2. **证据档**：「AI 从 N 份证据读到 M 条事实」——已被采用的打钩、未用到的也列出（证明 AI 通读过，而不是只挑了用得上的）
3. **英文申诉信**：可编辑、可下载 PDF、可复制全文；**LLM 只写每笔扣款的段落，信件骨架由代码确定性拼装**（收件人、押金号、金额汇总、s 165 出示单据要求、回复期限、附件清单）——金额与法条编号绝不出错，信与卡片天然一致
4. **行动路线图**：按州从 `stateProcesses` 确定性组装（Fair Trading/CAV → NCAT/VCAT 路径、费用、时限）+ 邮件留证话术 + 抢先向 RTBA/RBO 发起 claim 的指引；存管黄卡作为第 1 步
5. **战报卡**（见 §3.6）

桌面端 ≥1024px 变双栏：左栏账本条 + 对照卡（主角），右栏 sticky 放信 + 路线图 + 证据档。

### 3.6 战报卡

可保存分享的图卡 + 产品二维码——分享即拉票。

- **主数字**：「AI 逐项找出 **$1,120** 可争议扣款」
- **副行**：「按此应退回至少 $3,374」
- 底部：押金 $3,560 · 索扣 $1,306 · 3 笔 · NSW 租赁法 5 条法条
- **措辞纪律**：不得写「帮我追回」——除非确实已追回。工具的战果是**找出可争议扣款**，不是拿回钱。
- 示例页的卡左上角固定打「示例案例」角标；真实结果页的卡不带角标；一律不用第一人称叙事（避免用户替虚构案例作证）

## 4. 预制示例案例（默认体验路径）

- **静态预生成、零 API 调用**；文案逐字手工打磨
- **形态：零 API 全流程重放**——点进 `/sample` 后用静态数据自动播放一遍完整过程（证据飞入 → 字段自动填 → 事实逐条浮现 → 对照卡逐张翻开 → 结果页），全程约 17 秒（2026-07-26 实测 16.8s），可「跳过」直达结果。理由：投票者看到的是**过程**而不只是结果，同时给视频提供零 API 风险的素材源。
- 案情（NSW，按真实小红书案例改编）：押金 **$3,560**、房东索扣 **$1,306**

| # | 扣款项 | 金额 | 结论 | 依据 |
|---|--------|------|------|------|
| ① | 退租专业清洁 + 地毯蒸洗 | $780 | ❌ 不合法 | 入住报告记载 "Carpet: existing stains noted"（s 30 推定为正确）· s 51(3)(c) 判断清洁标准须考虑入住时状况 · s 19 笼统的专业洗地毯条款可能无效 |
| ② | 花园 / 草坪维护 | $340 | ⚠️ 待房东举证 | 已阅读的合约页中未见园艺维护义务条款 · s 165 房东须 7 日内出示条款与发票/报价 |
| ③ | 未付水费 | $186 | ✅ 合法，别争 | s 166 明列为可从押金中扣除的项目 |

- **可争议合计 $1,120 · 应退回至少 $3,374**
- 押金存管设为**黄色核实档**（押金交给中介、未收到 RBO 确认、未查过记录）→ 行动路线第 1 步「去 RBO 查你的押金号」。**不做第二个存管红警案例。**
- 四份证据：入住报告（**做成可点击定位高亮的 HTML 组件**，卡片引语点一下滚动高亮到 "existing stains" 那行）+ 租约 / 聊天截图 / 扣款清单（简版缩略卡）。地址、中介名、人名**全部虚构**。
- 页脚注明：「这是预载示例，你的案子会实时分析」

> v1.0 中的「墙面钉眼 ❌ 合理磨损」**已删除**：钉眼在 NSW/VIC 的 tribunal 通常被视为租客造成的损坏而非 fair wear and tear，把最弱的牌摆在最显眼处会伤可信度。

## 5. 非功能需求

- **移动优先**响应式（链接在微信群传播）；**桌面端需真正适配**：结果页/示例页双栏、首页 hero 双栏、向导单列加宽。断点、尺度与语义色见 `docs/design-tokens.md`（唯一事实源）
- **显式锁定浅色**（`color-scheme: light` + meta）：防微信安卓深色模式强制反色毁掉配色
- **无登录、无数据库**：会话内完成一切，不存储用户数据
- PDF 前端生成下载
- 简单限流防刷（API route 层）
- 页脚免责声明：「不构成法律意见」，必须在
- 报错兜底 + 加载动画：AI 调用失败要有体面的降级提示
- 成本预算：整场比赛 API 花费 $10-30 AUD（按 §7 选型，单次完整分析 ~$0.06 USD，预算足够跑上百次）

## 6. 入住留证模式 —— **已决定不做**

原「条件解锁」状态取消。首页愿景橱窗（即将支持：QLD/WA、**入住留证**、中介往来助手）即为终态。Gate A 仅作为主线健康检查，不再带解锁含义。

理由：它与「证据驱动的退租维权闭环」这条差异化叙事几乎不加分，而在深夜做「要不要动工」的判断本身就有成本。

## 7. 技术方案（已确认，勿更换）

- Next.js（App Router, TypeScript, Tailwind CSS v4）+ Vercel 部署
- **OpenAI 三段分工**（常量集中在 `lib/ai.ts`，换模型只改一处）：

| 常量 | 模型 | 用途 | 参考单价（/1M） |
|------|------|------|------|
| `EXTRACT_MODEL` | `gpt-5.4-nano` | 上传瞬间的字段预填 | $0.20 / $1.25 |
| `FACTS_MODEL` | `gpt-5.6-luna` | 读证据出事实（**产品命门**） | $1.00 / $6.00 |
| `ANALYZE_MODEL` | `gpt-5.6-luna` | 对照法条出逐项结论与信件段落 | $1.00 / $6.00 |

  - 单次完整分析约 **$0.062 USD**，低于原方案 gpt-4o 的 $0.076
  - **升级梯子**（读不准入住报告时）：`FACTS_MODEL` → `gpt-5.6-terra` → `gpt-5.6-sol`
  - **降级梯子**（延迟或参数不兼容时）：→ `gpt-5.1` → `gpt-4.1`
  - **开工第一件事跑冒烟测试**：真实调一张扫描版入住报告，量延迟并确认能否准确读出 "existing stains" 那一行
  - API key 仅在服务端（API route），绝不进前端
- **法条不建向量库**：NSW/VIC 押金法规整理成结构化资料，按州直接塞 prompt 上下文（引用更稳定）

## 8. 法条资料需求（最大翻车点 = 引用错法条）
